# JASCOV (Lab06-2) — บันทึกการดิ้น 14 รอบ แล้วยอมแพ้

ชุดไฟล์นี้จำลอง "คนที่ idea ถูกตั้งแต่ต้น แต่สะดุดจุดเล็ก ๆ ทีละอย่าง" เพื่อดู
**กระบวนการคิดแบบ debug ไล่ทีละรอบ** ว่าจุดไหนที่มักมองข้าม แล้วแก้ตรงไหน

โค้ดทุกไฟล์ **ไม่ใส่คอมเมนต์** (ให้เหมือน attempt จริงของคน) คำอธิบายอยู่ในไฟล์นี้

โจทย์: หา `p ∈ [0,1]` ที่ทำเวลา `D/speed(p)` น้อยสุด ติดเงื่อนไขเชื้อเพลิง
`burn(p)·(เวลา) ≤ F` → หา `p` มากสุดที่ `burn(p)/speed(p) ≤ F/D` แล้ว cap ที่ 1
โดย `speed(p)=5+10√p`, `burn(p)=2p³+p`

ค่าอ้างอิง `1.in` → `7.532325 / 5.333333`

## กับดักที่ทำให้ "แก้ไม่ตก"

เส้นทางนี้จริง ๆ **ถูกครบตั้งแต่รอบ 7** เหลือปัญหาเดียว แต่มองข้ามเพราะย้อนแย้งกับสัญชาตญาณ:

> "จะเร็วต้องใช้ `scanf/printf`" ← ความเชื่อผิดที่ทำให้ติดลูป
> ความจริง: `cin/cout` + `sync_with_stdio(false)` เร็วพอ **และ** อยู่ในไลบรารีที่อนุญาต
> → ได้ทั้ง "เร็ว" และ "ถูกกติกา" พร้อมกัน แต่คนไม่เชื่อ เลยสลับไปมาระหว่าง
> TLE (ถูกกติกา) ↔ 0 (เร็วแต่ผิดกติกา) จนหมดแรง

จุดเล็ก ๆ ที่คนมองข้ามในรอบแรก ๆ:
1. **อ่านโจทย์ไม่ครบ** — ลืมเงื่อนไข F (v1) / `burn` เป็นอัตราต่อเวลา ไม่ใช่ต่อระยะ (v2)
2. **ชนิดตัวแปร** — `int` แทน `double` (v3)
3. **`fixed` หาย** — ตัวการ format WA ที่ชอบ regression ตอนรื้อโค้ด (v4, v5, v12)
4. **กฎ library** — วายร้ายตัวจริง ให้ 0 เงียบ ๆ ไม่มี error ให้ debug (v7–9, v13–14)

**เฉลยที่ถูก = `../06-2.cpp`** (verify แล้วผ่าน): `iostream` + `sync_with_stdio(false)`
+ `fixed<<setprecision(6)` + binary search `burn/speed ≤ F/D` cap ที่ 1
